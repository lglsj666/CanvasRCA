# RQ4.3：正式运行低利用率排查与调度修复

日期：2026-10-11。范围为运行调度，不改变科学方案。用户先要求立即停止，随后授权调度修复、静态检查与一致性核对通过后直接恢复正式全量，明确跳过新的 GPU smoke。

停止补充 CPU 准备任务后，仍保持 8 个 GPU 请求在途的 11 个采样均值回升到 86.36%。暂停前 400 秒的对应均值为 67.94%。时刻根据 progress 的墙钟/monotonic 对齐估算；后半段同时也减少了新 prefill，不能把这一自然观察当作对某个 CPU 因素的独立因果证明。

## 为什么 smoke 没有暴露问题

smoke 确认了 8 个准备进程和 8 个 GPU 请求槽位都曾工作，但其准备队列只有 18 项，CPU 工作很快结束。它没有测到正式运行中不断填充 RAM 队列的持续负载。之前把这种短队列利用率外推到正式稳态，性能验证覆盖不足。

还发现正式入口 OMP/MKL 为 8，smoke 为 1。小型 CPU 检查确认，原有 torch.set_num_threads(1) 在八个 Python 请求线程内都返回 1，因此不能仅凭环境变量差异断言它就是全部原因。CUDA 分配回收平均 0.39 秒，也不足以单独解释生成段的增长。

最受当前证据支持的方向是宿主调度/资源竞争：准备进程绑定了前八个物理核，但 GPU 宿主线程没有排除这些核及其 SMT 同胞；同时大量软件绘图持续运行。现有记录没有逐线程调度剖析，保留这个证据边界。

## 修复与一致性

- 前 8 个物理核供 8 个准备 worker；后 8 个物理核供 GPU 宿主进程。亲和性覆盖已经存在的 native threads，未来线程继承，排除 SMT 核共享。
- 准备进程及后续子进程使用 nice 5；GPU 保持通常优先级。正式与 smoke 的 BLAS/OpenMP 环境统一为 1。
- 8 路 GPU 并发、prefill/forward 锁、8 个 CPU worker、连续 RAM 预取和字节容量保护均保留；没有加入磁盘缓冲。
- 利用率采样增加 CPU 活跃数、预取队列、逐槽 decode 步数和宿主 CPU 时间；完成记录增加实际线程亲和性和 CPU 时间，便于后续定位。
- 增加 `run.sh stop`，验证拥有的 formal PID/进程组后直接 SIGKILL，不等待请求排空。已有原子完成标记与中断恢复规则不变。

静态检查通过，功能代码 3,582 行。三个小型宿主调度安全检查通过：物理核/SMT 不重叠、核不足时拒绝共享、拒绝误杀复用 PID。这不是重跑全量 CPU 回归，也不是 GPU smoke。

一致性检查保留 314 个提交与 406 个受保护文件的哈希；2,632 位置队列逐字节不变。71 个函数/类定义保持不变；对模型路径去掉新加入的观测字段后，AST 与旧版一致。权重加载、BF16、融合内核、模型计算、输入、解码和评分保持原样。renderer 与 Codex.md 未修改。

v11 使用绑定当前源指纹的独立静态凭据和用户 GPU 豁免，不把旧 smoke 改写为新版本通过。正式运行已按最新授权从 314 个完成位置恢复，启动监控另存；持续吞吐是否改善，以监控结果为准。
