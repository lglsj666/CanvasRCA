## 故障与证据

22:40:29，vLLM EngineCore 报告 `Split/replayed prefill is not registered` 并退出。
已完成 2,795/4,832 个位置；HTML_SEMANTIC 为 81/220，HTML_PLOT_CODE 为 82/220。
七个请求收到 EngineDeadError，一个请求停留在 started，主进程一直显示 draining。
确认引擎已经退出后，仅终止实验自有进程组。已提交结果均保留。

原启动日志报告 13.66 GiB KV cache、208,457 token 等效容量，40,960 上下文的最大并发估计为 5.09。
出错时八个在途 HTML 输入分别为 23,494、29,120、29,978、31,423、31,147、29,252、28,707、27,542 token，合计 230,663，尚未计输出。
原程序只限制八个请求，没有为其后续输出保留缓存。
上游调度器在缓存不足时可以抢占并重新处理含已生成 token 的序列，即使 chunked prefill 关闭；这与本实验仅允许一次完整 prefill 的算子边界冲突。

使用已安装 vLLM 的原生 KVCacheManager、相同混合组结构和上述真实输入长度，离线重现八个输入无法同时分配。
原故障日志没有保存触发检查的 before/length 或抢占计数，因此不能逐步重放当时的精确调度顺序。
容量不足及不支持重算的接口组合得到日志、源码和分配回归支持；新增诊断会明确记录意外抢占及输入边界。

## 修复范围

1. 从已加载引擎取得实际 KVCacheConfig，按原生共享池和每个 full-attention/Mamba 组的块大小计算容量，扣除不可用 null block。
2. 每个请求进入 GPU 前，为完整输入加原有 8,192 输出上限预留全部缓存块。八路提交保持，超过真实容量的请求在 RAM 中按先进先出等待。较短视觉请求仍可八路同时运行，不统一降低并发。
3. 请求完成或失败后释放预留；取消等待不遗留队列头。未知缓存类型和不支持的 Mamba 模式显式失败。
4. 同步等待每秒检查引擎存活和登记截止时间。引擎死亡时，挂在 RPC 中的请求也进入基础设施失败；错误清理 RPC 有界，死引擎不再发送清理 RPC。
5. 保留完整 prefill、单 token decode 及算子计数检查；出现意外抢占直接报错。新增缓存等待时间、实际预留、峰值和抢占计数，避免把等待误报为推理时间。
6. 用户在修复中明确授权把本实验 `gpu_memory_utilization` 从 0.75 提高到 0.80。它是 vLLM 整体显存预算比例，不是全部用于 KV cache；准入仍基于启动后实际容量。没有修改项目共享模型配方或 Codex.md。

模型权重、BF16、解码采样、冻结提示/图像、token 选择及位置、P 算子数学定义、attention 采集与评分均保留。
现有结果不重答；八个未提交请求按基础设施恢复重新执行，原失败记录保留。孤立 started 请求已核实没有完成标记或回答轨迹后，明确记为引擎故障。
引擎请求交错可能变化，不能保证随机生成逐字一致；实际运行开销单列修订，不能假装调度与显存预算未变。
