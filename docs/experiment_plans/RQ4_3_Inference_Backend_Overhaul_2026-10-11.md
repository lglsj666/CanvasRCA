# RQ4.3：统一批处理后端整体改造方案

2026-10-11。实施更新：统一 vLLM v13 后端已完成，静态检查、14 项离线回归及 43 份真实输入的 token/位置翻译检查通过。用户明确授权“这次跳过 gpu smoke，完成后直接启动全量实验”。GPU smoke 标记为用户跳过，不标记为通过。部署前正式队列为 374/2632；保留所有提交和 8 次先前诊断操作造成的未提交中断及其恢复记账。有效恢复后连续观察 180.10 秒无新增基础设施失败，观察结束 405/2632，后续审计 410/2632；实际 decode batch=8。短窗口平均 GPU 利用率 82.43%，不宣称长期性能达标；详细启动失败、修复与限制见部署报告。

## 决定

停止在八个独立 `generate(batch=1)` 上叠加调度补丁。以 **vLLM 的迭代级批处理和缓存管理为目标后端**，一次整合本实验所需的模型适配、CPU 供给、输出约束、attention 测量和恢复机制。所有 arm 使用同一实现；不采用“普通臂 vLLM、P 臂 HF”的静默拆分。

这是运行后端改造，不是新增科学实验。原队列、图像、选择结果、位置定义、P 算子数学定义、权重、BF16、输出要求、评分和原子提交保留。旧实现与已有结果冻结；新后端另有版本与身份，时延不能跨后端直接混算。没有通过完整适配核对前，不声称 vLLM 迁移已经可用。

本次先固定整体设计，再形成一个完整、可审查的大补丁。实施中可以在未激活的版本内修正问题，但不再逐个补丁重启正式实验。不得将旧 smoke 的通过继承为新后端已通过。

## 已知问题及证据边界

- 目前八个请求分别执行完整 batch-one forward，没有真正合批；forward 锁只串行主机提交，不代表 GPU 内核绝对不能重叠。
- 正式运行有上百个已准备请求，CPU 供给不足不是这个观察窗口的主要解释。
- 语法处理包含逐 token 的 GPU→CPU 往返；独立抽样后 HF 又对单点分布抽样。应在统一引擎内保留相同输出规则并消除重复工作。
- v12 固定 KV 存储后，237 个满在途采样的 GPU 利用率仍仅 72.30%，不能标为性能通过。
- smoke08 的 85.58% 来自三例、18 个请求的短队列；正式病例、形状、任务和准备持续时间不同，没有证明长期性能。
- 历史本地 vLLM 配置 `configs/vllm_inference_local.yaml` 为 `enforce_eager: true`；RQ3.21 客户端并发为 36。不能将历史接近 100% 利用率归于 CUDA Graph，也不能忽略它与当前八并发的负载差异。
- 没有成功的 CUDA profiler 时间线。线程快照和源码支持结构性问题，但不支持某个开销占总时间多少的精确说法。

## 为什么优先使用成熟引擎

[ORCA（OSDI 2022）](https://www.usenix.org/conference/osdi22/presentation/yu)给出迭代级调度及选择性合批；[vLLM/PagedAttention](https://arxiv.org/html/2309.06180)将 KV 管理与请求合批共同设计。这直接对应当前缺少的能力，而不只是增加 Python 线程。

[PyTorch GPT-fast](https://pytorch.org/blog/accelerating-generative-ai-2/)表明静态缓存应与解码编译相配合，解释了为什么只改缓存不足。[HF 连续批处理文档](https://huggingface.co/docs/transformers/main/continuous_batching)也区分合批、图回放和调度重叠。资料可以确定优先方向，不能保证这个混合架构与实验算子组合的具体利用率。

优先级固定为：真正的解码合批 → 统一缓存及批量采样/语法处理 → 降低 CPU 往返 → 对兼容解码路径启用 CUDA Graph。单独安装 FlashAttention 不构成整体方案：48 个线性层已走 FLA，16 个标准 attention 层使用 SDPA；SDPA 已具备选择融合内核的能力，实际选择仍需运行证据。

## 调度合同

1. 单一 GPU 引擎实际合批活跃请求的下一个 token；没有八份独立 generate 循环。
2. CPU 保持八个 worker 和 RAM 预取；GPU 请求并发保持用户登记的八个，不擅自恢复历史 36。
3. 同一引擎处理所有 arm。组关系、选择与审计元数据仅控制已登记算子，不进入额外文本诊断输入。
4. 按原要求保留完整 prefill，不启用会拆分科学算子的 chunked prefill。decode 由迭代级调度接续；KV 和混合线性状态由引擎维护，不每请求清空 allocator。
5. 保留 40960 context、8192 输出、0.75 显存利用率，不量化、不删证据、不降低输出预算以换速度。
6. CUDA Graph 是合批后的附加优化，只覆盖已核对的解码路径；[vLLM 图模式](https://docs.vllm.ai/en/latest/design/cuda_graphs/)必须与混合状态更新兼容，不能为捕获图跳过 P 干预或测量。
7. smoke 和正式共用队列驱动、模型调用、预取、提交与采样实现，只允许输入范围、预算和停止条件不同。
8. 去除依赖 SIGUSR1/faulthandler 的在线栈诊断；使用不会向运行进程发送诊断信号的外部指标。曾经的诊断中断保留记录。

## 在恢复前完成的验证

### 不增加诊断调用的检查

- 静态与依赖检查：隔离扩展、不改变上游库或旧实验、五模块限制、全部输出与启动边界。
- 独立数值检查：token/位置恒等、辅助分支与原参考计算、线性状态、batch 边界、不同请求交错、结束/补入、同一随机状态和输出约束。
- 离线运行测试：八 CPU worker、RAM 背压、假模型合批、错误传播、原子写入中断、恢复与引用。旧已通过且不受影响的 CPU 资格不重跑。

### 真实模型验证

最新执行授权覆盖此前的申请说明：完成受影响离线检查后直接恢复正式队列，不新增 smoke 调用。离线通过不构成真实模型数值等价或性能通过；正式启动时检查原生批处理、算子分支计数、输入绑定、attention 与提交。未解决语义或基础设施错误会触发停止并保留中断记录。新后端使用原生独立请求随机流，不声称与 HF 逐字相同。当前保留 eager 模式，尚未启用 CUDA Graph。

验收使用同时覆盖长文本、不同图像长度、普通/干预算子和 QA 的固定混合负载；CPU 准备持续工作，执行正式的相同循环。样本选择不读取 MRR。检查实际合批大小、prefill/decode/CPU 等待、output token/s、calls/min、端到端时延、OOM、记账和输入绑定。

GPU 利用率按完整稳态请求区间报告，包含实际 prefill 和 decode，单列启动与排空；同时给采样时长和波动。目标维持用户已接受的约 85.58% 水平，并要求真实吞吐改善。短时峰值、减少有效工作、仅提高利用率但吞吐下降，都不算通过。

只在整个补丁验证完成后部署一次，不再反复以正式队列试错。现有 374 个结果全部保留，后端版本单独标记；若性能仍未达标，记录失败和阻塞，不自动启动下一轮零碎优化。
